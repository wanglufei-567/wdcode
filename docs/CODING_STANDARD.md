## wdcode **AI Coding** 工程规范

### 一、文档定位

本文件是 `wdcode` 仓库的 **AI Coding** 与工程质量规范真值

它约束个人站应用、共享代码和基础设施配置，目标是让这个长期维护仓库具备稳定边界、可读实现、可验证变更和可回滚部署

`docs/SPEC.md` 只维护本规范入口，不复制完整规则

### 二、编码前置原则

任何 AI 或人工编码任务开始前，必须按顺序阅读：

1. `README.md`
2. `docs/SPEC.md`
3. `docs/ARCHITECTURE.md`
4. `docs/CODING_STANDARD.md`
5. 目标目录自己的 `docs/SPEC.md`
6. 涉及生产运行时继续阅读 `docs/DEPLOYMENT.md`
7. 涉及 UI 时继续阅读后续建立的设计规范和现有样式系统

动手前必须明确：

- 本次任务属于个人站应用、基础设施还是外部应用接入
- 影响哪些模块、运行时、域名和消费者
- 是否改变镜像、端口、环境变量、数据卷或路由契约
- 数据从哪里来，经过哪些转换，最终由谁消费
- 哪些逻辑是纯计算，哪些逻辑存在网络、文件、浏览器或服务器副作用
- 需要执行哪些验证，失败时如何回滚

已经通过文档确认的工程形态不得被临时偏好隐式推翻

### 三、目录组织原则

目录必须表达责任，不按文件类型无边界堆放

目标结构：

```text
wdcode/
  apps/
    personal-website/
      docs/
      src/
      public/
  packages/
    shared-package-if-needed/
  infra/
    caddy/
    compose/
    scripts/
    docs/
  config/
    test/
    typescript/
  docs/
  tests/
```

结构按实际需要渐进创建，禁止为了看起来完整而建立空目录、空配置或虚假入口

目录规则：

- 根目录只保留仓库入口和 Workspace 级核心配置
- 应用放入 `apps/`
- 只有被两个以上模块真实消费的稳定代码才进入 `packages/`
- 生产路由、编排和运维脚本放入 `infra/`
- 全局文档放入 `docs/`
- 子模块专属规则放入该模块的 `docs/`
- 构建产物、运行缓存、测试报告和生产数据不得进入源码结构

### 四、模块与依赖边界

#### 4.1 个人站应用

个人站负责页面、展示编排、访问外部内容投影和自身运行契约

个人站不得：

- 导入 `infra` 实现
- 控制其他服务生命周期
- 直接读取生产 Docker Socket
- 持有全局路由和证书逻辑
- 复制外部项目的完整业务真值

#### 4.2 基础设施

`infra` 负责声明和执行生产运行关系

`infra` 可以依赖：

- 应用公开的镜像引用
- 内部端口、健康检查和环境变量契约
- 明确的持久化数据要求

`infra` 不得依赖：

- 兄弟仓库内部源码路径
- 外部应用私有模块
- 开发者机器上的临时构建产物
- 未写入契约的隐式启动顺序

#### 4.3 共享包

共享包必须保持稳定、无应用反向依赖

- 共享类型和 contract 不依赖具体页面
- 纯工具不访问网络、文件系统、DOM 或生产环境变量
- UI 包不包含部署逻辑
- 生产代码不依赖测试工具
- 只有明确复用和边界稳定时才提取共享包

### 五、数据流与副作用

数据转换链路必须能够顺序阅读，副作用必须可定位

- 网络请求放在 client、gateway 或 adapter 边界
- 文件和内容读取放在明确的数据源模块
- 环境变量只通过集中配置模块读取和校验
- 浏览器状态、缓存和持久化状态不得伪装成同一种数据
- 缓存、降级、重试、超时和权限行为必须显式表达
- 运行时目录读取、Markdown 请求和应用构建必须在类型和文档中区分

个人站展示 `DebrisRecord` 内容时，必须通过显式配置的只读挂载目录读取，不能静默扫描挂载根以外的本地目录

### 六、代码可读性

- 类型名、函数名、变量名和常量名必须表达领域语义
- 一个函数只承担一个可复述的职责
- 复杂流程拆成有业务语义的 helper
- 路径、端口、域名、TTL、重试次数和状态码使用命名常量或配置
- 错误处理、空值语义和降级路径必须显式
- 避免隐藏的全局状态和导入即执行副作用
- 不为减少行数压缩控制流
- 不为追求抽象统一引入没有第二个真实消费者的层

配置代码同样遵守可读性要求，不能依赖只有作者知道的命名、目录位置或命令顺序

### 七、**JSDoc** 与注释

JSDoc 用于沉淀边界、来源、消费者和误用风险，不逐行复述代码

以下对象默认需要 JSDoc：

- 导出函数和命名函数
- React 组件及可复用 Hook
- 可复用 helper
- API client、内容 loader 和数据 adapter
- 环境变量解析和运行时配置
- 缓存、降级、重试和权限相关函数
- 文件读取、内容仓库同步和发布脚本入口
- 部署配置生成、验证和回滚相关函数

JSDoc 应根据实际需要说明：

- `@description`：职责、所在工程层、存在原因和消费者
- `@param`：来源、约束、空值和默认值语义
- `@returns`：结果、失败、降级和空值语义

高价值注释应解释：

- 为什么存在反直觉实现
- 第三方协议或运行时的特殊行为
- 缓存、并发、证书、网络、权限和数据兼容风险
- 为什么更简单的写法在当前边界下是错误的

禁止使用注释掩盖模糊命名，也不得以减少噪音为由删除已被认可的高价值 JSDoc

### 八、配置与环境变量

- 根目录只保留 Workspace 入口配置
- 前端构建和测试配置放入可发现的应用或 `config/` 边界
- **Caddy**、**Compose** 和运维配置统一放入 `infra/`
- 配置路径调整后必须同步脚本、文档和 **CI** 引用
- 不保留废弃平台配置和失效兼容层
- 环境变量必须有 `.env.example`、语义说明和启动期校验
- 服务代码不得把宿主机固定端口当作内部契约
- 生产密钥、证书状态和业务数据不得提交到 Git

### 九、文档治理

文档按下列真值分层：

- `README.md`：定位、当前状态和阅读入口
- `docs/SPEC.md`：项目范围、责任目录和依赖方向
- `docs/ARCHITECTURE.md`：为什么需要架构、运行链路和长期边界
- `docs/CODING_STANDARD.md`：**AI Coding** 与工程质量规范
- `docs/DEPLOYMENT.md`：生产契约、验证和回滚
- 子模块 `docs/SPEC.md`：模块自身职责和接入契约

文档规则：

- 当前实现、目标架构和未来选项必须显式区分
- 全局文档不重复子模块实现清单
- 子模块文档不复制全局编码规范
- 权威清单只保留一份，其他文档通过链接引用
- 代码、配置、命令或职责变化时同步更新对应真值文档
- 不把临时讨论、未经验证的猜测或单次任务偏好写成永久规则

### 十、基础设施代码规则

基础设施变更具有更大故障半径，必须额外满足：

- 只有 **Caddy** 发布宿主机 `80/443`
- 每个服务使用唯一、稳定的 Compose 服务名
- 镜像引用使用不可变版本，生产不只依赖 `latest`
- 外部应用通过镜像接入，不通过兄弟目录 `build.context` 接入
- 数据卷变更必须说明兼容性、备份和恢复路径
- 路由变更必须说明域名、目标服务和健康验证
- 应用更新默认定向部署，不无差别重启整个 Compose 项目
- 运维脚本默认启用严格错误处理，并在破坏性动作前解析精确目标
- 删除容器、镜像、卷或生产文件前必须确认作用范围和可恢复性

### 十一、测试与验证

验证范围必须匹配风险，默认顺序为：

```text
static checks
  -> typecheck
  -> unit tests
  -> build
  -> integration tests
  -> end-to-end tests
```

个人站 UI 变化根据风险验证：

- 类型检查和单元测试
- 生产构建
- 关键页面和路由
- 响应式布局、可访问性和浏览器控制台
- 外部项目链接

基础设施变化根据风险验证：

- Compose 配置解析
- **Caddy** 配置校验
- 镜像可拉取性
- 服务健康检查
- 外部 HTTPS 路由
- 数据卷和环境变量映射
- 定向回滚演练

不能把命令退出码为 `0` 直接等同于业务成功，验证必须覆盖本次变更的真实消费者

验证结束后清理构建产物、测试报告、临时缓存和运行时生成数据

### 十二、**AI Coding** 协作纪律

AI 执行任务必须遵守：

- 先读文档和结构，再修改文件
- 先确认责任所有者，再选择目标目录
- 先检查 contract，再改变跨模块行为
- 保持既有风格和已确认架构，不引入无关依赖
- 发现用户已有改动时保护其内容，不擅自覆盖或清理
- 不删除用户认可的注释、文档和结构
- 不越过明确的审阅、提交、推送或生产发布边界
- 卡外问题只报告，不顺手扩大修改范围
- 完成后报告变更文件、验证结果和未验证项

当用户意见、文档和现有实现发生冲突时，先核验事实，再明确指出冲突和需要裁决的真值，不自行选择方便实现的一方

### 十三、完成标准

一次变更只有同时满足以下条件才可以报告完成：

- 文件放在正确责任目录
- 依赖方向未被破坏
- 对外 contract 已更新或保持兼容
- 必要 JSDoc 和边界注释完整
- 对应真值文档已同步
- 风险匹配的验证已经执行
- 未生成需要清理的临时文件
- 未执行用户没有授权的提交、推送或生产变更
